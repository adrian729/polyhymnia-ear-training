# App
- This repo (`polyhymnia-ear-training`) is the ear-training product SPA: Vite + React 19 + TypeScript, Tailwind CSS v4 (`@tailwindcss/vite`, CSS-first, no `tailwind.config.js`), shadcn/ui, TanStack Router (file-based, `routeTree.gen.ts` committed).
- shadcn components live in `src/components/ui`, generated via the shadcn CLI, not hand-written.
- Class merging uses the npm `cn` package, never `clsx`/`tailwind-merge`. `cn build` (`scripts/cn-tables.ts`, run by Vite and Vitest) compiles merge tables from the classes in `src` and the theme's scales into gitignored `src/generated`. It reads only `styles/theme.css`, so every `@theme` declaration lives there; `src/lib/utils.ts` builds the one `cn` from them, so import `cn` from `@/lib/utils` everywhere, never straight from `"cn"`. The tables read the `--text-*` tokens, so `text-meta` merges as a size and never deletes a co-occurring `text-*-foreground` (`test/cn-type-scale.test.ts`). The scan cannot see class names built at runtime (`'p-' + size`): write them out whole.
- Vendored fonts (`src/assets/fonts`) are never served whole: the `scripts/font-faces.ts` Vite plugin splits them on every dev start and build (Junicode by Unicode range, the initials one file per letter), keeping every character and the OpenType features and axes the CSS requests. Output goes to gitignored `src/generated/fonts`. Declare new vendored faces in its `FACES`; never hand-pick subsets or edit generated files. The build also preloads, from the HTML, the Basic Latin file of the families the `PRELOAD_TOKENS` theme tokens name (body text and titles, on every page).
- Sheets: pages render `<Sheet>` (`src/components/SheetLayout.tsx`), never `PaperSheet` or elder-scrolls directly. The root layout keeps the main and sidebar sheets mounted across routes, so a navigation changes contents, not paper; the two materials live in `PaperSheet`. Things appear when ready, each wait capped by `--ready-wait` (`styles/surfaces.css`): the first screen waits for table, papers and fonts (`src/lib/first-paint.ts`), a page's text for its faces (`SheetLayout`), a later sheet for its artwork. `src/main.tsx` preloads what every first screen needs at startup and defers the rest until that screen is shown; before that, the HTML has already started the table and main paper (`scripts/artwork-preload.ts`), choosing each copy exactly as elder-scrolls will for the screen's density (`test/artwork-preload.test.ts`), else it downloads twice. It stays at low priority, so it never takes bandwidth from the app's script where the server honours priorities, and stops above 2x screens, where the larger copies delayed the first screen more than they saved. Below-the-fold content that should be there before the reader arrives (the home score) uses `NearView` with `prepare`: its code and fonts download after the first screen (`afterFirstScreen`), and only then does it render, two viewports ahead of the reader (one viewport missed the home score, which sits just past a single viewport below the fold); it never renders alongside the first screen. That deferred work is ordered so the nearest content is not starved on a slow link: a `prepare` registers with `prepareNearContent` and goes first, and speculative work (another page's paper, every initial letter, instrument samples, warmed images) runs through `afterNearContent` (`src/lib/first-paint.ts`), which waits for it, capped. Fetch fonts for later with `prefetchFontFiles`, never `document.fonts.load`, which would hold a newly opened page's text while it loads.
- Ornament and image assets are declared and generated, never hand-imported. They come from the Ducktape Assets library (`@ranx729/ducktape-assets`, pinned exactly): list the asset id in `ducktape.json` with `"masters": true` (lossless master only, since the app re-encodes), run `pnpm assets:sync` (`ducktape-assets copy`, then the generator; also the one command after bumping the pin), and commit the copied masters and `ducktape.manifest.json` in `src/assets/ducktape`; never edit or add files there by hand, and add new artwork to the library, not here. Then add one entry to `scripts/ornament-selection.json`: `group` (the generated module a page imports), `name` (how the page asks for it), `id` (the Ducktape id, `<set>/<asset>`), and `role` — `image` (needs `widths` for the srcset, none wider than the master; `"format": "avif"` for fine-coloured painted art; optional `flourish`: where a heading's text and rules meet the art), `frame` (needs `thicknessesPx`: the drawn border width in CSS px, or a narrow one and a wider one drawn from the `sm` breakpoint up; the border-image slice comes from the library's `render.frame` in the copy manifest), or `mask` (a transparent asset); with optional `quality`. Coordinates in `flourish` are master pixels. The `scripts/asset-manifest.ts` plugin (run by Vite and Vitest, like the fonts) reads `ducktape.manifest.json` (master size, `transparent`, frame slice) and writes per-group modules to gitignored `src/generated/assets`, sizing every copy as the app draws it — frame copies sized by the library's slice, every copy and mask rung capped at the master so nothing is upscaled — and fails the build on an id that was not copied, a master that is missing, or geometry off the master. The dev server regenerates when the selection or the copied manifest changes. A page consumes a group through `imageAsset`/`frameAsset`/`maskAsset` (`src/lib/assets.ts`) and the matching component (`OrnamentImage`, `BorderFrame`; `<Ornament asset={…}>` for masks), never a master path and never a hard-coded slice, width or density. There is no divider role: if a repeating divider is ever needed again, take a `render.tile` asset from the library and rotate it at build time with sharp from its master. Adding a group is one file, adding an asset is one id and one line; `src/generated-assets.d.ts` types the modules so `pnpm typecheck` needs no generated files.
- Encoding and render rules: the generator encodes lossy by default — illustrations `quality=82` WebP; fine-coloured painted art uses AVIF (`&format=avif&quality=60`) because WebP stores colour at half resolution and greys it; masks stay lossy WebP since WebP keeps alpha exact; only vector art (logos) is `&lossless`. Render colour art through `ResponsiveImage` (explicit `sizes`, intrinsic `width`/`height`, `placement`) and never a raw `<img>` (`test/images.test.ts` enforces it). Art only CSS can draw (a border or background image, as `BorderFrame` does) imports a copy for each drawn width and density and picks them with inline `-webkit-image-set()` (`imageSet` in `src/lib/assets.ts`); the prefixed alias is required (inline styles get no fallback from the CSS build, and unprefixed `image-set()` needs Chrome 113 or Safari 17). Stylesheets never reference images: Vite ignores the sizing queries there and ships the master. Logos come from the SVG sources in `src/assets/logo` (`src/lib/logo.ts`); the favicon PNG is rendered from its SVG by `scripts/favicon.ts` into gitignored `public/polyhymnia-favicon.png`. The Vectorian sources in `src/assets/ornaments` stay raster (their licence forbids vectors) and go through `Ornament`/`OrnamentCorners`, whose ladder is separate from the generated assets. Compare each new lossy image against its lossless master at the drawn size before shipping.
- Load performance: `node scripts/bench.mjs <label>` records emitted and first-screen bytes; `node scripts/bench-timings.mjs <label> [--scroll] [--routes /] [--runs N]` drives headless Chrome against `pnpm preview` (production, for the service worker) and reports FCP, first-screen-visible, load, transferred bytes and requests per route; diff two captures with `node scripts/bench-timings.mjs compare <a> <b>`. Captures land in gitignored `benchmarks/`. Below-the-fold art is lazy by default (`placement="below-fold"`), which keeps it out of the `load` event, so judge it by scrolled bytes rather than load; warm a below-the-fold image after the first screen with `OrnamentImage`'s `warm` or `warmImage` (`src/lib/warmup.ts`) from the page that shows it, never at a route module's top level: that code ships in the entry chunk and runs on every page.
- Caching: GitHub Pages sends `max-age=600` for every file, so `sw/service-worker.ts` (vite-plugin-pwa `injectManifest`, production builds only) serves returning visitors: page loads fetch the app shell network-first, hashed `assets/` are cache-first, and `samples/` and the favicon are stale-while-revalidate. Keep new files under one of those rules (build assets get hashed names), test caching with `pnpm preview`, never `pnpm dev`, and retire the worker with `VitePWA({ selfDestroying: true })`. `src/main.tsx` reloads once when a deploy removed a chunk the open page still needs.
- Text is justified and hyphenated app-wide from the `sm` breakpoint up (`body` in `src/index.css`), as manuscripts set it; phones start-align, since their lines are too short to justify. Centre or start-align with a utility only where a place needs it.
- Colors: Catppuccin (Latte light, Mocha dark), primary = pink. `primary` is for fills (exact Latte/Mocha pink); pink text, links, rings and notation highlights use `primary-strong` (AA-safe on light backgrounds). Scales in `src/styles/palette.css`, semantic shadcn tokens + notation `--pn-*` mapping in `src/styles/theme.css`. Use semantic tokens or palette scales, never raw color values. Never pure black or white (`white`/`black` are remapped to Latte base / Mocha crust).

# Packages
- Notation, theory and sound come from the published `@polyhymnia/*` packages (github.com/adrian729/notation, music-theory, web-audio), imported only through their public exports; never copy package code here. Fix package bugs in their repos.
- Local package development: clone those repos next to this one (or set `POLYHYMNIA_SRC`) and run `pnpm dev:link`; `pnpm dev:unlink` before committing.
- MNX is the only score format; app-private helpers that return plain MNX (`mnxBuild`) are allowed. Quiz data about notes lives in the app, keyed by MNX note id, never in the document.
- The app owns time: notation never runs clocks; the app drives `setPlaybackTick` from `@polyhymnia/web-audio` playback and mnx-score `performance()`.
- Pitch, interval, chord, scale and key logic comes only from `@polyhymnia/music-theory`.
- Render check: committed `.mnx.json` scores must lay out with `layoutScore` without errors or unexpected `mnx-unsupported` (`test/scores-render.test.ts`).
- Third-party audio libs or samples only behind the `Instrument` seam, pinned; ask before installing.
- Samples never load as a whole instrument up front: `src/lib/sound.ts` plays through a web-audio `createSampler`. Once the first screen is idle (and at once after an instrument change) it warms coarse to fine: one sample per octave, then one every third semitone, then stops; exact samples load when their notes first play. A note plays at once from its own sample or the nearest loaded one within a tritone, repitched; only a play with a note that has neither waits, for its own samples and at most 0.5 s, then plays with the best loaded (borrowed or the synth). Audio known before it plays (a score, an answer the user is building) calls `prepareNotes`. Samples hold about 3 s (guitar is cut at 3.1 s, see `public/samples/CREDITS.txt`): the longest note played is 2 s; a longer note releases when its sample runs out, so longer notes need longer samples.

# Tests
- Add a test only to prevent a real regression: a contract or a bug that was actually fixed. Otherwise don't.
- New behavior → at most a few tests for its distinct branches. Never one test per constant, option, or trivial mapping; never restate the implementation.
- Fixed bug → one regression test that fails without the fix. Table-driven over copy-paste; no cross-products.
- Test only through public entry points; never export internals for tests. Never weaken an assertion to go green.
- Agents: run tests with `--reporter=dot`.
